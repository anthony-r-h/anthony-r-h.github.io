This is the site operating manual for this repo.

## What This Site Is

- Static site built with **Jekyll**.
- Gulp pipeline handles:
  - merging YAML config files,
  - compiling theme values into SCSS,
  - bundling JS,
  - launching local dev server.

## Folder Structure (Practical View)

```text
.
|- _posts/              # All posts (markdown)
|- pages/               # Standalone pages (about, plan)
|- _layouts/            # Page/post/list layout templates
|- _includes/           # Reusable partials (header, footer, cards, etc.)
|- _sass/               # SCSS partials
|- _plugins/            # Custom Liquid tags and filters
|- assets/              # Built/static assets served by Jekyll
|- files/               # Post media and downloadable project files
|- src/
|  |- yml/              # Source config split into multiple yml files
|  |- js/main/          # Source JS bundled into assets/js/scripts.min.js
|  |- js/preview/       # Preview/admin widget JS copied as-is
|  `- img/              # Legacy image sources; not processed by the current build
|- scripts/preview.mjs  # Lightweight server for an existing _site build
|- index.html           # Home page front matter entrypoint
|- contact.html         # Contact page front matter entrypoint
|- tags.html            # Tags page front matter entrypoint
|- search.json          # Search index generated from posts
|- sitemap.xml          # Sitemap template
|- _config.yml          # Generated final Jekyll config (do not hand-edit)
`- gulpfile.js          # Build orchestration
```

Jekyll publishes `files/` directly, except for camera raw files, `.bak` files, and `.log` files excluded in `src/yml/_config.yml`. The current Gulp build does not copy or optimize anything from `src/img/`; put new published media in `files/` or `assets/`.

## Which Layouts Exist and When to Use Them

Current layouts in `_layouts/`:

- `home.html`
  - Main home feed with card grid.
  - Supports include/exclude tag filtering.
- `list_view.html`
  - Text list style feed (used for plan page).

  - Standard post page layout.
  - Uses `post_ui` config + optional per-post overrides.

  - Generic content page wrapper.

  - Tag index/listing page.

  - Web ring page layout.

## Where Config Lives

Authoritative source config files are in `src/yml/`:

- `src/yml/site.yml`
  - Site identity and menu.
  - Home/list-view UI defaults.
- `src/yml/posts.yml`
  - Post layout and typography defaults.
- `src/yml/social.yml`
  - Social usernames for footer/schema links.
- `src/yml/theme.yml`
  - Core theme colors used by SCSS.
- `src/yml/advanced.yml`
  - Base URL, site URL, and language.
- `src/yml/_config.yml`
  - Includes all files above + Jekyll build/plugin settings.

Generated config:

- `_config.yml` at repo root is generated by Gulp from `src/yml/_config.yml`.
- Edit files in `src/yml/`, not root `_config.yml`.

## Key Settings You Will Actually Use

From `src/yml/site.yml`:

- `menu`: nav items.
- `email`: contact address source.
- `home_listing.include_tags` / `home_listing.exclude_tags`:
  - Default filtering for home feed.
- `home_grid.*`:
  - Grid behavior for home cards.
- `list_view_ui.*`:
  - Styling defaults for list pages.

From `src/yml/posts.yml`:

- `two_columns_layout`: enables/disables post sidebar.
- `post_ui.*`: post typography/spacing/colors.

From `src/yml/advanced.yml`:

- `baseurl`: subpath deployment (usually `""` for root domain).
- `url`: full production URL.
- `language`: site language code.

From `src/yml/theme.yml`:

- `themeColor`, `primaryDark`, `accentDark`, `lightGray`, `texts`, `contentBg`.

## Front Matter Cheatsheet

Typical post front matter:

```yaml
---
layout: post
title: "Post title"
subtitle: "Optional subtitle"
description: "Optional short summary for cards/search/SEO"
date: 2026-03-07
category: Tech
tags:
  - Tag1
  - Tag2
image: /files/path/to/image.jpg
optimized_image: /assets/img/optimized.jpg
math: true
toc: true
---
```

Post cards prefer `optimized_image` when both image fields exist. Social metadata uses `image` first, then falls back to `optimized_image` and the site default.

ToC in posts:

```yaml
toc: true

```

- Do not add manual ToC markdown (`* toc`, `{:toc}`) or HTML headings.
- The post layout renders the ToC via `_includes/toc.html` only when `toc: true`.

Math in posts:

```yaml
math: true
```

- This loads MathJax for that page.
- Use `$...$` for inline math and `$$...$$` for display math.

Local video embeds:

Chart config (optional):

```yaml
csv_chart:
  type: line          # line, bar, or scatter
  title: Progress
  show_title: true
  show_axis_titles: true
  show_y_ticks: true
  x_tick: month       # optional month-only x tick labels
  x: Date             # column name or index
  y:
    - ForceL
    - ForceR
```

Expression-based chart series:

```yaml
csv_chart:
  type: scatter
  x: Date
  y_label: Peak Force
  y_unit: lbs
  y_expr:
    - label: MeanForce
      expr: mean(ForceL, ForceR)
    - label: Balance
      expr: ForceL - ForceR
```

Chart display options:

- `csv_chart_show_gridlines` (page level) or `csv.chart.show_gridlines` (per table)
- Default is controlled site-wide in `post_ui.csv_table.chart_show_gridlines`
- Row filter support:

```yaml
csv_chart:
  filter:
    field: tag
    equals: Max
```

Weekly rollup + aggregate example:

```yaml
csv_chart:
  type: line
  title: Weekly Max Peak Force
  x: Date
  group_by: week
  y_agg:
    - label: Right
      op: max
      field: peak_right
    - label: Left
      op: max
      field: peak_left
```

Dual-axis derived series example:

```yaml
csv_chart:
  type: scatter
  y_label: Peak Force
  y_unit: lbs
  y2_label: SW
  x: Date
  group_by: week
  y_agg:
    - label: Right
      op: max
      field: peak_right
    - label: Left
      op: max
      field: peak_left
    - label: SW
      from_agg_expr: (Right + Left) / 135
      axis: right
      type: line
      color: "#f5c518"
      border_width: 4
      fill: false
```

## Including Markdown From Another Repository

I can keep a README or other documentation in its project repo and include it in a post at build time:

{% raw %}
```liquid
{% remote_markdown "https://raw.githubusercontent.com/OWNER/REPO/main/README.md" %}
```
{% endraw %}

I put the tag on its own line, with blank lines above and below it. It can sit between my own sections, or be the whole body after the post's front matter.

The URL must point to a public file on `raw.githubusercontent.com`, in the form `OWNER/REPO/REF/path/to/file.md`. I can use `main`, a tag, or a commit SHA as the reference. For branches containing `/`, I use a commit SHA to avoid ambiguity between the branch and file path. Private repositories and GitHub `blob` page URLs are not supported.

The build fetches the file and renders it with the site's Kramdown/GFM Markdown engine. Imported front matter is removed; the blog post keeps its own metadata. Remote Liquid tags and variables are treated as text rather than executed. HTML in the source is preserved, so I only include content I trust.

Relative paths are resolved from the imported file, including files in subdirectories:

| Source in `docs/README.md` | Result |
| --- | --- |
| `![Photo](images/photo.png)` | Raw image at `docs/images/photo.png` in the source repo |
| `[Guide](../guide.md#setup)` | GitHub file page for `guide.md#setup` at the same reference |
| `![Cover](/assets/cover.png)` | Raw image at `assets/cover.png` from the repo root |
| `[Section](#assembly)` | Anchor in the current blog page |

Inline and reference-style Markdown links/images work, along with HTML `href`, `src`, `poster`, and `srcset` attributes. Absolute URLs, protocol-relative URLs, and fragment-only links are left as written. CSS `url(...)` paths are not rewritten. Links to other Markdown files lead to GitHub; they do not import those files too. Imported headings keep their generated IDs, so repeated heading names across the post and included files can conflict.

The Markdown becomes part of the built page. Images and other linked media stay hosted in the source repo; they are not downloaded into this site. Each file is fetched once per build. A branch reference picks up changes on the next build, while a commit SHA pins the source and its rewritten media paths to that version. Changes in the other repo do not trigger a blog build automatically.

A missing file, failed download, invalid UTF-8, or file over 2 MiB fails the build with a `remote_markdown` error. There is no stale offline fallback. The plugin is `_plugins/tags/remote_markdown.rb`; its regression tests run with:

```bash
bundle exec ruby _tests/remote_markdown_test.rb
```

## Tag Strategy Reminder

- Home currently excludes `Plan` by default via `home_listing.exclude_tags`.
- Plan page includes only `Plan` via `pages/plan.md`.
- `planning_sections: true` groups the plan page into `Ideation`, `Planning`, `In Progress`, and `On Hold`. Set a post's `planning_tag` to one of those values; unknown or missing values fall back to `Ideation`.
- Tags are case-insensitive in filtering logic, but keep naming consistent anyway.
- The exact tag `Hidden` keeps a post out of home/list pages, tags, search, the sitemap, post pagination, and related-post links. The post is still available at its direct URL.
- Avoid empty tag values.

## Build / Dev Commands

Use Ruby `3.2.11` and Bundler `2.4.19`, matching `.ruby-version` and `Gemfile.lock`. With mise, prefix Ruby commands with `mise exec ruby --`; Gulp detects mise automatically. Audit the npm lockfile and resolve vulnerabilities before installing dependencies.

Install deps:

```bash
bundle install
npm audit
npm ci
```

Run local dev:

```bash
npm run dev
```

One-off build:

```bash
npm run build
```

Preview an existing build at `http://127.0.0.1:4000`:

```bash
npm run preview
```

Build and then preview:

```bash
npm run preview:build
```

If Jekyll fails on Windows with `_site` file permission errors, close apps/processes locking files under `_site/files/` and run build again.

## Deployment

`.github/workflows/pages.yml` builds and deploys to GitHub Pages on pushes to `master` or a manual workflow run. Feature branches do not deploy automatically.

The workflow runs Jekyll directly, including the custom plugins. It does not run Gulp, so after changing source YAML, theme values, or JavaScript I run `npm run build` locally and commit the relevant generated `_config.yml`, `_sass/_theme.scss`, and `assets/js/` files with the source changes.

The shorter repository guides are in `docs/`, starting with `docs/README.md`. Netlify CMS files in `admin/` are legacy configuration, not the current deployment workflow.

## Content Workflow (Quick)

1. Create a markdown file in `_posts/` named `YYYY-MM-DD-title.md`.
2. Fill front matter (`layout`, `title`, `category`, `tags`, optional `description`/`image`).
3. Write content in Markdown.
4. Use `Plan` tag if it should appear on `/plan/` instead of home.
5. Run `npm run dev` and verify home, post page, search, and tags page.
